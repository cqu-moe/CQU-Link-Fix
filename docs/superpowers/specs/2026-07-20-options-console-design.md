# CQU Link Fix 独立设置控制台设计

**日期：** 2026-07-20

**状态：** 已批准

**范围：** Chromium Manifest V3 / WXT 设置页

## 1. 背景

当前 WXT 生成的 Manifest 将 `options_ui.open_in_tab` 设为 `false`。Chrome 因此把设置页嵌入扩展详情页的窄模态框，而现有页面按至少 720px 宽度和长页面阅读设计，导致内容被挤压、滚动距离长、控制项之间的关系不清楚。

用户希望参考 Tampermonkey 的管理方式：设置不再局限于浏览器提供的小弹窗，而是在独立标签页中使用完整页面空间。目标不是复刻 Tampermonkey 的旧式视觉，而是采用它的整页管理空间与高信息密度，形成更现代、清楚的本地控制台。

## 2. 目标

- 从 Chrome 扩展详情页或扩展弹窗进入设置时，在独立标签页打开设置页。
- 让运行状态、总开关、可选权限和规则状态在首屏内可理解。
- 用紧凑列表替代大块卡片与过量留白，提高规则管理效率。
- 保留现有设置数据格式、权限边界、后台写入协议和即时保存行为。
- 保持键盘操作、状态播报、窄屏适配和错误可见性。

## 3. 非目标

- 不改变 URL 改写规则、优先级或匹配逻辑。
- 不新增或扩大必需、可选主机权限。
- 不改变自定义规则的精确域名限制或权限租约流程。
- 不增加遥测、远程规则、账号体系、导入导出或搜索功能。
- 不在本次工作中重做扩展弹窗；弹窗只继续提供进入完整设置页的入口。
- 不引入 React、Vue 或新的 UI 框架，继续使用现有 HTML、CSS 和 TypeScript DOM 渲染边界。

## 4. 设计方向

界面定位为“重庆大学本地网络控制台”。视觉采用暖白背景、墨色文字和 CQU 红状态强调，避免现在巨大的展示型标题、衬线主视觉和杂志式纵向留白。

页面强调三点：

1. **运行状态先于品牌展示。** 用户进入页面后先看到扩展是否运行、权限模式是否开启以及最近一次操作结果。
2. **规则是可扫描的数据。** 名称、作用范围、状态和错误在同一行内呈现，减少卡片间跳读。
3. **危险与异常有明确层级。** 权限拒绝、保存冲突和规则未加载使用文本与图形状态共同表达，不只依赖颜色。

## 5. 页面架构

### 5.1 独立标签页

在 options 入口页声明 WXT 支持的 `manifest.open_in_tab=true` 元数据，使构建产物生成：

```json
{
  "options_ui": {
    "page": "options.html",
    "open_in_tab": true
  }
}
```

现有 `browser.runtime.openOptionsPage()` 调用保持不变，由 Chromium 根据 Manifest 在独立标签页中打开或聚焦设置页。

### 5.2 桌面布局

页面使用三层结构：

- **顶部工具栏：** 紧凑显示 CQU Link Fix、版本、本地运行标识、全局启用状态与最近一次操作状态。
- **左侧导航：** 固定显示“概览”“内置规则”“自定义规则”“暂停站点”，点击后滚动到相应区域；使用 `IntersectionObserver` 根据进入视口的分区更新当前项选中态。
- **主工作区：** 最大可读宽度约 1280px，按导航顺序呈现管理内容，不把整页拉伸到超宽屏边缘。

顶部工具栏和左侧导航在常见桌面视口中保持可见，用户操作长规则列表时仍能看到扩展状态和页面位置。

### 5.3 窄屏布局

视口不足以容纳侧栏时：

- 左侧导航变为顶部可横向滚动的分段导航；
- 工作区改为单列；
- 规则行允许描述与作用范围换行；
- 主要开关和删除按钮仍保留至少 44px 的可点击区域；
- 页面不设置会造成横向溢出的固定最小宽度。

## 6. 功能分区

### 6.1 概览

概览首屏包含两个主要控制：

- **启用链接改写：** 现有总开关，停用时保留所有本地设置。
- **全部 CQU 域名模式：** 现有可选权限开关，明确标注开启时会触发 Chromium 权限请求，并保留学校未发布资源仍不可访问的说明。

两个控制使用水平状态面板，但总开关在视觉层级上更高。控制处于等待后台响应时显示忙碌状态并暂时锁定，避免重复提交。

### 6.2 内置规则

继续按核心认证、重要站点、IP 名单和附加修正分组，但每组使用紧凑规则列表。每条规则包含：

- 启用开关；
- 规则名称；
- 简短说明；
- 匹配范围；
- 当前状态，包括启用、停用、版本锁定或未加载。

默认关闭且不可手动启用的内置规则保留锁定原因和辅助技术可读描述。DNR 校验失败在对应规则行内显示，不能只写入全局状态栏。

### 6.3 自定义规则

输入区与已添加规则放在同一工作区：

- 输入框直接说明只接受精确 CQU DNS 域名；
- 主按钮使用“申请权限并添加”；
- 权限拒绝、输入无效、冲突和租约清理异常继续显示具体原因；
- 已添加规则沿用与内置规则一致的列表结构，并额外提供删除操作。

自定义规则的 permission request 必须继续在原始提交手势的同步调用链中启动，页面重构不得引入会破坏 Chromium 用户手势判定的异步中间层。

### 6.4 暂停站点

暂停站点使用紧凑列表展示精确主机和“恢复改写”操作。空状态说明暂停操作从扩展弹窗发起，不增加第二套输入入口。

## 7. 状态与错误反馈

现有 `#status` 继续作为 `role=status` 的单一实时播报源，但视觉位置从页面底部移至顶部工具栏下方的状态条。状态条支持：

- 中性：正在读取、正在申请权限、正在保存；
- 成功：设置已加载、规则已启用或删除；
- 错误：后台通信失败、设置冲突、权限拒绝、全局同步失败。

规则专属错误仍放在对应行内。自定义输入错误仍与输入框关联。错误消息使用文字、图标和颜色共同表达，并在状态变化时通过现有 ARIA live 区域播报。

## 8. 数据流与模块边界

数据流保持现状：

1. options 入口初始化控制器；
2. 控制器从后台读取 `SettingsSnapshot` 和 DNR 状态；
3. options model 将内置规则、保存设置和校验错误组合为显示模型；
4. renderer 创建或更新 DOM，并将用户事件交回控制器；
5. 控制器通过后台协议替换设置，或在用户手势中发起可选权限流程；
6. 保存完成后重新渲染并更新全局与行内状态。

本次允许扩充 renderer 所需的展示类名和语义容器，但不把存储、权限或浏览器 API 调用移动到 renderer。HTML 保留控制器依赖的稳定元素 ID；动态规则继续使用 `data-rule-id`、`data-custom-rule-id` 等测试和事件标识。

## 9. 可访问性

- 所有开关保留原生 checkbox 与可见 label，不使用只靠 CSS 的伪开关。
- 键盘焦点使用高对比轮廓，不能被 sticky 工具栏遮挡。
- 左侧导航使用真实链接指向分区锚点，并提供当前区域状态。
- 错误、锁定和忙碌状态保留 `aria-describedby`、`aria-disabled`、`aria-busy` 和 live region。
- 文本与背景、强调色与背景满足常用正文和控件的可读对比度。
- `prefers-reduced-motion` 下关闭非必要过渡。

## 10. 测试与验收

### 10.1 自动化验证

- 增加构建产物断言，验证 `manifest.json` 中 `options_ui.open_in_tab === true`。
- 保留并更新 options 控制器单元测试，确保总开关、内置规则、自定义规则、排除项、冲突和错误行为不变。
- 保留 loaded-extension E2E，验证打包后的 options 页面无控制台错误并能读取与写入设置。
- E2E 继续通过页面稳定 ID 和 `data-*` 属性操作，不依赖纯视觉类名。
- 运行 `pnpm verify`、`pnpm test:e2e`、`pnpm zip`、zip 完整性检查和 `git diff --check`。

### 10.2 视觉验收

在独立标签页中人工检查以下视口：

- 1440px 及以上桌面宽度：侧栏、工具栏和规则列表层级清楚，内容不过度拉伸；
- 1024px 左右宽度：主要控制与规则信息无裁切；
- 约 768px 及以下宽度：导航转为顶部形式，页面无横向滚动；
- 长规则范围、行内错误和空分组不会破坏列表对齐。

### 10.3 完成条件

- Chrome 从扩展详情页和弹窗入口打开独立设置标签页。
- 首屏可辨认总状态、总开关和可选权限状态。
- 四类内置规则、自定义规则和暂停站点均可正常管理。
- 所有原有权限边界和设置写入规则保持不变。
- 自动化验证通过，且桌面与窄屏视觉验收没有阻塞问题。

## 11. 风险与约束

- Chromium 原生可选权限提示仍属于浏览器 chrome，自动化无法可靠点击；现有 headed/manual gate 保持不变。
- Sticky 导航和状态条不能遮挡锚点标题；各目标分区必须设置覆盖工具栏高度的 `scroll-margin-top`。
- 规则行密度不能以牺牲中文可读性为代价；说明文本允许换行，而操作列保持稳定。
- 视觉重构不得改变 permission request 的用户手势时序或后台拥有设置写入权的架构边界。
